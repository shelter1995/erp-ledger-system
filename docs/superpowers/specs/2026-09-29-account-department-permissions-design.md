# 部门、账号与模块权限调整设计

日期：2026-09-29。核对基线：`e510e5058f4d520f8ecaaa0b4c314ed20d3217ef`。
状态：用户已确认设计并授权本地实施；真实账号迁移与生产发布单独执行。

## 1. 目标与已确认规则

部门账号默认只访问本部门，台账管理员默认可访问全部门，超级管理员拥有全部权限。台账管理员的全部门范围不覆盖模块限制。各账号分别配置业务模块和系统管理模块。

关闭采购模块时，不允许访问采购页面、采购专用接口、采购明细和明细导出；允许通过已获授权的台账、仪表盘查看采购汇总。销售模块采用相同规则。所有汇总先过滤部门，再计算结果。

用户可自行修改密码。仅超级管理员能重置密码，重置后登录必须先修改临时密码。修改或重置密码后旧会话失效。

首期不做任意字段级授权、不做部门级备份恢复、不改变已修复的导入业务算法。本地开发、真实账号迁移和生产发布分开验收。

## 2. 现有实现及设计选择

已核对文件：`backend/app/auth.py`、`routers/auth.py`、`routers/system.py`、`routers/orders.py`、`routers/ledgers.py`、`routers/history.py`、`audit.py`、`backup.py`、`docs/erp_ledger_schema.sql`、`src/App.tsx`、`src/components/LedgerScreen.tsx`。

现有账号使用角色和 JSON 权限，业务模块已有新增、修改、删除权限；读取多数仅校验登录和部门。空部门范围表示全部门，`system_admin` 同时承担管理功能和部门绕过。前端统一加载各业务数据，台账详情和导出包含跨模块明细。密码重置没有强制改密和会话版本控制。

选择：保留现有业务接口和写入逻辑，增加统一授权层、显式部门范围与管理页面拆分。相比只增加菜单开关，该方案能保证直接调用接口不能越权；相比引入外部身份平台或通用策略引擎，改造范围较小，适合当前规模。

特别注意：财务视图以 `CASE WHEN ol.source_preserved = 1 THEN ol.line_department ELSE p.department END` 判定实际部门。项目部门不能替代来源明细部门；这是对早期讨论中“随项目归属”的精化。

## 3. 账号和部门模型

账号类型：`department_user`（部门账号）、`ledger_admin`（台账管理员）、`super_admin`（超级管理员）。账号类型提供默认配置，普通账号的实际权限来自明确保存的权限集合，不能随角色模板调整自动扩权。

为 `erp_user` 增加：

| 字段 | 用途 |
| --- | --- |
| account_type | 三种账号类型 |
| home_department_id | 所属部门，可与授权范围不同；部门账号必须设置 |
| scope_mode | `none`、`selected`、`all`；空集合永不等于全部门 |
| log_scope | `self`、`department`、`all`；还必须具备日志查看权限 |
| must_change_password | 首次使用新建临时密码或重置密码后强制改密 |
| auth_version | 密码、权限、范围、启停状态变化时递增 |
| authorization_version | 标明账号已按新模型完成映射 |

保留 `permissions_json` 作为操作权限集合；增加账号与部门关联表保存 selected 范围。旧字段仅用于迁移输入，不作为新授权失败时的回退路径。

增加统一部门表，包含稳定 ID、唯一名称、启用状态，以及唯一映射的历史名称别名。部门新增、停用、改名由超级管理员操作，入口位于账号与权限页面。有关联的部门不得硬删除。

为减少导入回归，首期保留业务表已有部门文本，不批量改写历史台账；授权层从稳定部门 ID 解析规范名称及别名。部门改名保留旧名称别名，新增业务只使用规范名称。不可识别的部门在导入预览中报错，不自动创建部门。

所属部门、授权范围、日志范围独立；部门账号默认 selected=[所属部门]，台账管理员默认 all。none 表示无业务数据，可用于仅管理账号的运维账号。selected 必须非空。空部门业务记录仅 all 范围可见，普通部门账号不可见。all 必须显式保存。

## 4. 权限目录和组合

保留已有新增、编辑、删除键，增加读取和管理操作键。未知权限键提交返回 422，不静默接受。

| 模块 | 权限键 | 界面表达 |
| --- | --- | --- |
| 仪表盘 | dashboard_view | 不可访问 / 可查看 |
| 台账 | ledger_view | 不可访问 / 可查看 |
| 基本信息 | order_view、order_entry、order_edit、order_delete | 不可访问 / 仅查看 / 查看及修改，另勾选删除 |
| 销售信息 | sales_view、sales_entry、sales_edit、sales_delete | 同上 |
| 采购信息 | purchase_view、purchase_entry、purchase_edit、purchase_delete | 同上 |
| 跨部门转移 | department_transfer | 独立操作权限 |
| 维护与导入 | maintenance_view、ledger_import、data_replace | 页面、批量导入、全局维护替换分别配置 |
| 账号与权限 | accounts_view、accounts_create、accounts_update、accounts_disable | 页面及账号操作分别配置 |
| 日志 | logs_view | 页面权限与 log_scope 组合 |
| 备份恢复 | backups_view、backups_create、backups_verify、backups_restore | 查看、创建、校验、恢复分别配置 |

查看及修改映射为 view+entry+edit，删除必须同时具备 view。兼容迁移可保留旧账号仅新增或仅编辑的非标准组合，并在界面显示“自定义”，不强行补齐写权限；编辑这类账号时可明确选择标准档位。

台账自身不增加一套重复编辑权限；从台账新增、编辑、查看业务明细时检查对应模块权限。汇总导出随 ledger_view 授权。完整台账模板数据导出、完整历史期次导出必须同时具备 order_view、sales_view、purchase_view；不得以 ledger_view 单独放行。

ledger_import 是跨基本、销售、采购数据的独立特权，需 maintenance_view，允许明确授权的账号执行整表导入，不要求其拥有各模块交互编辑权限；授权界面说明它可能写入三个模块。仍须校验全部来源行的实际部门和已有目标记录范围。导入报告只显示本账号获授权操作的批次，不开放任意历史批次或业务明细查询。

data_replace 只允许 all 范围账号获得；现有维护替换为全局清理和重建，首期不实现部门替换。backups_* 为全局能力，操作权限需 backups_view，授权界面明确其不受部门过滤保护；默认仅超级管理员拥有，显式授权恢复需 all 范围。自动导入前备份保留为受控内部步骤，不因此给导入账号备份页面权限。

## 5. 后端授权和数据边界

统一判定顺序：有效身份及 auth_version → 强制改密限制 → 超级管理员/操作权限 → 数据范围 → 业务前置条件。不得通过 system_admin 旧权限键绕过部门。

模块接口必须在服务端授权。列表、详情、历史、模板、导出、批量编辑、导入状态、下拉选项均纳入路由清单。缺少模块权限返回 403；对象不在部门范围内返回 404，不泄露是否存在。列表过滤在 SQL 中执行，分页 total 与汇总采用同一过滤条件。

新建、编辑、删除校验实际所属部门；修改部门同时校验修改前后范围。跨部门转移还需 department_transfer。框架转移涉及全部来源行，必须校验全部原部门及目标部门，禁止只通过框架中的一条可见明细获得整框架修改能力。保持原始导入字段作为历史证据，权限依据有效归属；转移实现须明确更新受影响的有效部门，不能只更新 project 而留下来源明细仍归旧部门。

批量操作任意一项越权则整批拒绝并回滚。导入预览后被撤权、调部门、停用，再提交必须重新授权；不信任预览时的权限快照。权限更新与进行中的业务写入应明确事务顺序，在业务写事务内再次核对权限版本；使用相同账号行锁顺序避免更新授权与提交写入之间发生检查后越权。

## 6. 汇总、明细和前端加载

仪表盘与台账汇总由后端提供专用 DTO，不依赖浏览器预先获取完整基本/销售/采购明细。现有统计口径、金额精度、过滤条件和空态保持一致。

台账汇总允许：部门、框架/项目、客户、负责人、订单数、订单金额、采购金额、交付收入/成本、收付款合计、开收票合计、应收应付、毛利润及状态等已有汇总指标。可提供框架下的订单级经营汇总，但不包含合同编号、供应商交易明细、逐笔发票/收付款、附件和编辑原始行。

台账弹窗的销售、采购明细分别按权限显示并按需获取；模块关闭时保留对应汇总卡片，隐藏明细区和跳转。汇总查询接口不能通过 expand/include 参数返回受限明细。

台账已有供应商、开票日期等关联过滤，在服务端实现受部门约束的存在性筛选，保留正常查询功能；不向未授权账号返回供应商明细或逐笔票据。汇总导出使用与界面一致的专用导出 DTO，不复用现有含全部业务列的 91 列导出。

前端建立统一权限上下文和路由守卫。加载账号获授权且当前页面所需的数据；部门选项来自独立的授权部门接口，不再依赖台账数据。首次登录进入首个可访问页面；无业务权限可进入个人账号页面。

权限变更后旧令牌失效，前端清空业务缓存和选中明细并重新登录，不继续展示撤权前数据。后端 403 不得导致其他已授权模块整页不可用。

## 8. 防止账号管理提权

超级管理员可以设置全部账号；其他账号管理员不能管理超级管理员、不能设置超级管理员类型、不能修改自己的权限/范围/状态。

普通账号管理员仅能创建或管理满足以下全部条件的普通账号：目标原有与新权限均为操作者权限子集；目标原有与新部门范围均被操作者覆盖；目标日志范围不超过操作者。all 不得由 selected 授予；拥有某个部门的日志权限不等于拥有全部日志授权能力。

普通账号管理员不得转授账号管理类权限、全局维护替换、备份恢复或 department_transfer；这些特权仅超级管理员授予。账号类型选择也不能隐式赋予超过上述范围的模板权限。重置密码始终仅超级管理员可执行。

至少保留一个启用且可登录的超级管理员。停用、降权、迁移均采用事务和数据库锁保护该约束；并发请求不能各自通过计数后将最后两个超级管理员同时移除。首期以停用代替永久删除，新管理界面不提供永久删除，原永久删除接口限制为超级管理员，保留现有停用前置条件。

## 9. 日志范围

新增结构化日志范围数据：操作人账号 ID、操作人部门快照、事件类型（业务/系统）、全部涉及部门 ID 集合、是否能确定范围。部门归属使用事件发生时快照，人员调动不改变历史日志可见性。

self：只显示本人单部门业务事件和本人账号安全事件；跨部门、系统管理、范围不明事件不因操作者相同而放行。department：只显示涉及恰好一个部门、该部门落在授权范围内的业务事件。all：可查看全部事件。跨部门事件仅 all 可见，避免前后快照泄露其他部门数据。

旧日志无法可靠重建涉及部门，保留原文并标记范围不明，只对 all 可见；不根据当前操作者部门猜测历史范围。日志读取权限独立于业务模块权限，授权界面明确日志可能包含业务变更前后内容。密码、令牌、密码哈希不写入日志。

## 10. 密码与会话

新增 POST /api/auth/change-password，验证旧密码、新密码及确认值一致，新密码不能与当前相同。新设置密码采用 12–128 字符，允许空格及中文，不要求固定字符组合；旧密码仍可登录并通过改密升级，不批量重置现有密码。

新建账号和超级管理员重置均设置 must_change_password=true 并递增 auth_version。令牌包含稳定账号 ID 和 auth_version，服务端每次核对数据库状态。临时登录态仅可读取本人信息、修改密码和退出，不能访问业务或管理接口。

修改成功递增版本、清除强制改密标志，前端清理登录状态并要求使用新密码重新登录；所有旧令牌失效。停用、恢复、权限变更也递增版本，恢复账号不会复活旧令牌。普通改密、强制改密均记录不含敏感值的审计日志。

## 11. 迁移与旧账号核对

新增一次性版本化迁移，不能在每次启动时依据旧 admin/system_admin 重新赋权。现有导入权限迁移保持幂等，不能恢复人工撤销的 ledger_import。

分两步：先做只读盘点和候选映射报告，再基于核对后的显式映射执行。报告不包含密码哈希、令牌或密码；包括账号标识、启停、旧角色、实际权限、旧部门范围、新账号类型候选、新权限候选、歧义原因。

| 旧配置 | 候选处理 |
| --- | --- |
| system_admin 或 admin 默认权限 | 标为超级管理员候选，必须核对；不能仅凭角色名自动升级 |
| 明确部门范围普通账号 | 映射 selected；保留原有实际写权限，补充原来确实可读模块的查看权限 |
| 空部门范围非超级管理员 | 标为范围待核对，不擅自改成 all，也不直接在线上切换成 none |
| 同名/别名冲突或缺失部门 | 标为待核对，不猜测合并 |
| 显式空权限列表 | 保持不获得写入及管理权限，读取能力按旧实际行为列出供核对 |
| 已停用账号 | 保持停用，保存映射并更新会话版本 |

存在未核对的账号映射、部门冲突或没有有效超级管理员时，迁移预检阻止正式切换。报告绑定账号配置摘要；正式执行时发现源配置发生变化则重新盘点，防止覆盖期间人工撤权。

部门清单从账号范围、项目部门、来源明细部门取并集，只去除首尾空白，不自动合并近似名字。真实账号清单仅在确认目标数据库环境后读取；当前文档没有读取业务数据库，不能把模拟账号当作现有账号。

迁移保持业务记录数、金额、日期、公式、历史来源及旧密码哈希不变。DDL 与账号数据映射分阶段校验，不能假定 MySQL DDL 支持整体回滚。切换时使旧令牌全部失效，前后端配套发布，备份账号权限表及部门映射。回滚只使用受控备份和匹配版本，避免退回空部门即全部门的行为造成意外放权。

业务备份继续不包含账号和日志。新部门目录属于授权配置，不随业务恢复覆盖；恢复预检核对业务中的部门名称均能被当前目录解析，不能通过恢复旧备份新增或恢复授权。服务器全库备份仍由运维流程负责。

## 12. 代码边界与验证

后端新增统一授权模块、部门目录路由、版本化迁移与只读映射报告工具；修改 auth、业务路由、history、audit、导入授权入口和备份恢复预检。保留业务金额计算及来源导入算法。

前端修改 permissions、api、App 和各业务页面；从 SystemScreen 拆出四个管理页面、共享账号权限编辑组件和个人密码页面；台账/仪表盘改为服务端汇总数据，不用开放其他模块读取权限解决依赖。

必须覆盖的验收反例：

1. 甲部门账号通过列表、详情 ID、历史、导出、批量编辑均不能访问乙部门。
2. 同一框架含甲乙两部门来源行，甲只能得到甲的汇总；来源部门为空不回退到项目部门放行。
3. 采购关闭、台账打开，采购汇总正确；采购专用接口、弹窗明细、91 列及期次完整导出均被拒绝。
4. 销售关闭、仪表盘打开时统计正常且不请求销售明细；基本信息关闭亦不影响合法汇总。
5. 仅查看不能新增/修改/删除；可编辑不自动获得删除、导入、替换、转移。
6. 导入混入越权部门整批失败；预览后撤权则提交失败且无写入。
7. 仅日志、仅账号、仅备份等账号只能进入对应页面；单个接口 403 不拖垮其他授权页面。
8. 普通账号管理员不能给自己提权、管理高权限目标、扩大范围或重置任何账号密码。
9. 跨部门日志、范围不明旧日志只对 all 可见，部门账号调动不改变历史事件归属。
10. 重置后旧令牌失效，临时密码登录不能绕过强制改密；改密后旧密码及旧令牌均失效。
11. 并发停用/降权仍保留最后一个有效超级管理员。
12. 迁移重复执行不扩权；旧配置变化使预检失败；人工撤权重启后不恢复。
13. 部门改名后旧数据可按别名识别，未授权部门不可通过选项、数量或报表泄露。
14. 业务恢复不覆盖账号、日志和部门授权；不认识的部门阻止恢复。
