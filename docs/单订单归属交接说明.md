# 单订单归属交接

## 操作入口

基本信息列表 → 行内眼睛图标 → 当前订单交接。

“当前订单交接”修改同一订单下全部明细的客户经理、部门、分公司和三级团队，不影响同框架其他订单。“整个框架交接”仍用于统一调整框架内全部订单。弹窗显示本次影响的订单数和明细数；包含无权维护的数据时禁止提交。

订单号通过“变更订单号”单独维护，改号保留历史编号和内部关联。项目名称、货物名称继续使用行内编辑。普通录入和原表导入订单使用相同交接入口；原表内容保留作为来源证据。

## 权限

账号需要基本信息查看、修改，以及“归属交接（当前订单 / 整个框架）”权限。底层权限标识仍为 `department_transfer`，已有授权继续有效。交接还需覆盖涉及的全部原部门和目标部门；拥有此权限不会自动扩大数据范围。

## 数据兼容

在 `sales_order` 上增加 `ownership_overridden`、`department`、`branch_company`、`account_manager`、`team_level3_name` 和 `manager_history`。未交接的订单维持原有归属规则；交接后优先读取订单归属。客户经理历史按订单保存，避免单订单交接污染框架内其他订单的历史查询。整个框架交接会同时更新所有活动订单和框架默认归属。

销售、采购、基本信息、汇总、导出、导入批次查看和写入版本校验使用有效部门。备份随 `sales_order` 保存新增字段；旧备份缺少字段时使用数据库默认值，保留原先归属规则。

现有启动建表流程先执行新增列迁移，再重建视图。本改动需后端、数据库结构和前端配套更新，不能只发布前端。此说明不表示已在服务器升级或迁移。

## 手工验收

1. 在测试环境选择同框架两个不同订单 A、B，记下客户经理和部门。
2. 从 A 的详情进入“当前订单交接”，确认影响范围，修改客户经理并填写原因。确认 A 的全部明细更新，B 保持原值。
3. 给 A 更换部门，分别用原部门和目标部门账号检查可见范围；无交接权限的账号不能提交。
4. 变更 A 的订单号，确认 A 的历史号仍可查询、B 的订单号不变；编辑 A 的项目名称或货物名称，确认 B 的归属不变。
5. 用客户经理筛选并勾选“包含历史负责人”，确认 A 的独有负责人不会匹配出 B；核对历史导出和操作日志。
6. 在测试环境验证“整个框架交接”及备份恢复，确认全部订单的新归属与各自历史保持一致。
