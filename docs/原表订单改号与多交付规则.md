# 原表导入：订单流转与多次交付

2026-09-29 确认：原表中的订单号路径可以表达合并和拆分，不限于一条全局线性的改号链。

## 当前归属和历史查询

- 每条明细以其路径的最后一个编号确定当前订单；同项目、同当前号归到同一订单。
- `A/C` 和 `B/C` 表示不同旧订单汇入当前订单 C。
- `A/B` 和 `A/C` 表示原订单 A 的明细分别进入 B、C；两个当前订单保留独立。
- 一个编号可以同时是某些明细的历史号、另一些明细的当前号。导入不会自动迁移其他批次已经存在的明细。
- `sales_order_number_history` 在原表导入中作为关联编号查询索引，允许不同当前订单共享旧号；其并集不能视为一条发生顺序。
- 每条明细的有序路径由 `ledger_raw_row.raw_json.values[12]` 保留，API 的 `order_number_path`、详情和 Excel 导出使用该路径。
- `order_number_history` 用于关联号搜索。界面用顿号展示关联集合，用箭头展示本明细路径，避免给不同分支编造先后顺序。
- 连续 `/` 或 `／` 是冗余分隔符；不生成空编号。单个编号仍须满足 64 字符限制。

普通编辑和旧版历史校验没有被全局放宽；以上规则用于用户确认的原表保真导入。

## 交付与收票

多个交付日期分别落为多条交付记录。金额多笔时按位置对应；只有一个总金额时等分，按分精度取值，尾差归最后一笔。数量按六位小数同样拆分；未交付余额只保留一次。

采购收票多个日期对应一个总金额时等分；一个发票号沿用原值，不编造新的发票号。其他财务类型保留既有解析规则。

财务视图按明细聚合交付，避免重复放大订单金额。合计编辑入口遇到多条交付时，不允许用一组合计覆盖明细；未修改交付的保存保留原数据。

## 原值保留

### 销售订单日期（2026-09-29 确认）

原表导入的 F 列日期写入 `order_line.line_order_date`，每条明细独立保留，包括空值。首页、明细查询和 Excel 导出通过财务视图读取此日期；后续导入同一订单的其他年份数据，不改变已有明细的年份归属。单条和批量编辑原表明细日期只更新本明细；普通录入订单继续使用订单级日期。

升级与旧备份恢复从 `ledger_raw_row.raw_json.values[5]` 回填日期，使用 `line_order_date_initialized` 标记保证可重试且只初始化一次，避免覆盖后续修改或主动清空的日期。没有原始日期归档时中止升级，不猜测共享订单日期。

毛利润统一按 W－AC－BL＋BM 计算，BN 仅作为原始证据保留。原表 W、AC、BL、BM 保留计算精度，汇总后统一四舍五入到分。2026 年最终数据按 F 列筛选 2026 年，结果为 63,747,637.65 元；不能先将每行毛利润舍入后再汇总，否则为 63,747,634.85 元。

客户单位、最终用户和区域平台按来源明细保留，允许同订单、同子项目中存在正常历史差异。旧数据升级从已归档原表回填新增字段；后续编辑只更新当前明细，不覆盖其他年份。误设为日期格式的金额和发票号从 XLSX 原始数值恢复，只改内存副本。采购合同号支持 255 字符；采购和销售发票号、开票单据号、回款通知单号使用 TEXT 保存较长原文，索引保留前 128 字符。桌面原文件不由导入器修改。
