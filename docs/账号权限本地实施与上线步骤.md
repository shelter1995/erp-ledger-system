# 账号权限调整：本地实现与切换步骤

## 本次范围

实现部门账号、台账管理员、超级管理员，显式指定部门/全部门/无业务数据范围，业务模块查看与维护权限，以及四个独立管理页面。采购模块关闭后，台账与仪表盘仍提供采购汇总；采购专用明细接口拒绝访问。销售模块同样处理。

新建账号或重置密码后，用户必须自行改密；新密码 12–128 字符。改密、重置、调整权限和启停账号都会使旧登录凭证失效。部门改名保留历史名称，部门停用禁止新授权及新业务；部门账号读取按有效部门别名过滤。

当前改动仅在本地代码与 `erp_ledger_test_auth_*` 隔离数据库验证。没有迁移真实账号，没有推送或部署。业务备份不包含账号、部门目录、授权关系和日志；它不能替代升级前全库备份。

## 实施方式与兼容边界

- 启动只补充表结构，不自动把旧账号映射成新权限；未迁移旧账号会拒绝登录。
- `tools/account_permissions.py report` 只读盘点，不输出密码或密码散列；输出需要保存在受控目录。
- `prepare` 是可重复的增量结构准备，MySQL DDL 不能靠事务回滚；必须先备份。
- `apply` 要求逐账号 `reviewed: true`、源数据摘要不变、至少一名有效超级管理员。已有新权限账号或已应用的迁移不允许再次覆盖。
- 空部门范围不再代表全部门。旧账号清单中提示“空部门旧账号”时，必须人工确认 `all` 或 `none`。
- 原来的 `system_admin` 拆成管理页面和操作权限；不会作为部门越权通行证。
- 权限数据与业务数据分离，恢复业务备份不会恢复已撤销的账号权限。未知历史部门必须先登记目录再恢复。
- 旧内部账号创建接口参数已经替换为新模型；外部若有自编账号管理脚本，须改用 `/api/auth/users` 的新字段。

## 你需要手动操作的阶段

本地开发与自动测试不需要手动操作。正式切换时，需要你确认真实账号归属与权限清单，并在维护窗口按下面步骤执行。不要只更新代码后直接重启旧账号系统。

### 1. 准备与备份

确认目标机器、实际项目根目录、Python 运行环境和数据库名，使用既有全库备份流程保存升级前数据库及当前代码版本，并验证备份可读取。已有 Linux 全库备份入口为 `ops/backup/full-backup.sh`，配置方式沿用现有运维手册；不要把数据库口令写入聊天或命令输出。

以下命令从**目标项目根目录**运行；`你的业务库名` 必须替换为实际数据库名，必须与该环境 `MYSQL_DATABASE` 配置一致。Windows 使用下面的 Python 路径；Linux/容器内将解释器替换为该应用实际使用的 `python`，其余参数一致。不要在未确认容器名或项目位置时直接套用部署命令。

### 2. 只读生成清单

```powershell
backend/.venv/Scripts/python.exe tools/account_permissions.py report --database 你的业务库名 --file account-permissions-review.json
```

若输出文件已存在，命令拒绝覆盖；使用新的文件名保留之前核对结果。

逐个核对 `accounts[].candidate`：

- `account_type`：`department_user`、`ledger_admin`、`super_admin`。
- `scope_mode`：指定部门为 `selected`，全部门为 `all`，没有业务数据范围为 `none`。
- `departments`：selected 对应的部门名称列表，不能为空；其他范围使用空列表。
- `home_department`：部门账号必填，其他类型可为空。
- `permissions`：按设计文档权限目录填写，修改/新增/删除需同时有模块查看，管理操作需有管理页面权限。
- `log_scope`：`self`、`department`、`all`；同时需要 `logs_view` 才可打开日志。
- 每个确认无误的账号设置 `reviewed: true`，保留账号 ID 和原始 `source_digest`。

核对 `department_mapping`：键是历史部门名称，值是规范部门名称。不同历史名称可以明确映射到同一规范部门；映射不会改写原始台账文本。不得随意删除历史名称。

至少保留一个真实可登录且启用的超级管理员；不要把所有旧台账管理员都默认升成超级管理员。无权限的历史账号可以映射为 `none`，也可以在正式切换前按既有流程停用后重新生成清单。

### 3. 维护窗口应用

暂停账号变更和业务写入，确认没有正在执行的导入。使用已验收的新版本工具，但先不要向用户开放新服务。

```powershell
backend/.venv/Scripts/python.exe tools/account_permissions.py prepare --database 你的业务库名
backend/.venv/Scripts/python.exe tools/account_permissions.py apply --database 你的业务库名 --file account-permissions-review.json
```

遇到“账号或部门已变化”，重新 report 并重新核对，不手工修改摘要绕过检查。遇到已迁移提示，不删除迁移标记强行重跑；后续改权限通过账号页面完成。

成功后按既有部署流程启动新版本后端和已构建前端，全部账号重新登录。迁移保留旧密码；只有新建或被重置的账号强制改密。新系统首次初始化的管理员也强制改密，初始密码至少 12 字符。

### 4. 业务验收

1. 超级管理员检查部门目录及每个账号最终权限。
2. 用一个部门只读账号确认只能看到本部门，修改按钮不可用，直接访问未授权页面也不可用。
3. 关闭采购模块：台账应保留采购汇总，采购入口隐藏，采购明细不可访问。
4. 用台账管理员检查全部门范围，并逐个检查仪表盘、台账、基本、销售、采购的开关。
5. 为不同账号分别授权四个管理页面，确认互不捆绑。
6. 用户自行改密；超级管理员重置测试账号密码，确认旧会话失效，新密码登录后必须再次自行改密。
7. 用部门账号尝试跨部门单条及批量维护，确认拒绝且没有部分写入。
8. 核对导入预检、确认、报告，以及原有财务计算、历史查询和业务备份恢复。

### 5. 回退

若切换失败，保持维护窗口，使用升级前完整数据库备份及对应旧代码恢复。不要只退代码继续使用已经映射的新角色名；不要使用应用内“业务备份恢复”替代账号和结构回退。重新开放服务前再核对账号权限与业务数量。
